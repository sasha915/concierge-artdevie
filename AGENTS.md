- Desktop member presentation uses lg-only layouts or desktop-only variants of existing shared components; preserve all mobile classes and business logic to keep the validated mobile experience unchanged.
- Team presentation is scoped to AdminShell and admin routes; use team-theme tokens and existing member queries so member screens and access controls remain unchanged.
- Request history and reply templates are accessed only through authenticated team server functions; template writes require admin, and client-safe history/filter/insertion rules are isolated for tests without touching real requests.
- Request billing (lot 4.2): amounts and commissions follow src/lib/billing-rules.ts; invoice numbers come only from public.next_invoice_number(); request amounts are team-only and invoices are created by admins through server functions.
- Member notifications (lot 4.3) are in-app only: team server functions insert into member_notifications when profiles.notify_requests is true; members read their own rows and mark them read through mark_request_notifications_read.
- Request exchanges (lot 5.1): request_messages is read by members through RLS on their own requests only; every write goes through sendTeamMessage (team) or sendMemberMessage (member, author forced server-side). WhatsApp to the concierge is centralised in src/lib/notify-concierge.server.ts.
- Files, change requests and reviews (lots 5.2/5.3): members only SELECT through RLS (visible files, their own changes and reviews); every write goes through server functions in src/lib/messages.functions.ts (member) or admin.functions.ts (team); files are downloaded through 5-minute signed URLs from the private request-files bucket. Shared rules live in src/lib/request-actions-rules.ts.
- Proposals and recurring requests (lots 6.1/6.2): members only SELECT their own proposals, options and recurring rules; answering a proposal, creating a series and pausing it go through messages.functions.ts; sending/withdrawing proposals through admin.functions.ts. Occurrences are created 7 days ahead by public.generate_recurring_requests(), run daily at 06:00 UTC by the pg_cron job 'art-de-vie-demandes-recurrentes' (service-side only). Rules in src/lib/planning-rules.ts.
- Agenda, welcome questionnaire and statement (lots 6.3/6.4): getAgenda and getMemberStatement are team server functions; member answers live in member_preferences.*_choix / dates_membre (no member RLS access, read/write via getMyWelcome/saveMyWelcome); team notes in the same table stay internal. Statements are PDFs generated in the browser by src/lib/statement-pdf.ts (jsPDF). Rules in src/lib/agenda-rules.ts and src/lib/member-rules.ts.
- English version (lot 6.5): member-facing text goes through t()/tPair() from src/lib/i18n.ts; the French text is the key and src/lib/i18n-en.ts holds the English. Any new member text must be wrapped and added to the dictionary (src/lib/i18n.test.ts fails otherwise). Stored values (statuses, categories) stay French and are translated at display. /admin always renders in French. Member notifications are written in profiles.language at send time.
- Member space V4 (22 October): page background #241C33 (--background), panels #3B2D55 (bg-panel / bg-card), glass surfaces bg-glass with border-foreground/16; status colours in cards.tsx statusClass. The .eyebrow class already adds the parentheses: never write them in the text. Plan prices come from public.membership_plans; the WhatsApp webhook secret lives in Supabase Vault (notify_concierge_webhook_secret).
- Authorised contacts (lot 5.4): public.member_delegates (statuses en_attente / actif / refuse / retire, 3 open per member, one open delegation per email). Members SELECT their own rows; every write goes through src/lib/delegates.functions.ts (member invite/revoke, delegate actions) or admin.functions.ts (approveDelegate admin-only, refuse/revoke team). A delegate account is created with user_metadata.account_kind = 'proche' and gets no profile (handle_new_member skips it); it reads nothing through RLS — all its reads go through server functions that re-check delegationOf() on every call and return only safe columns (no amounts, invoices, proposals). Requests made by a delegate keep user_id = member and set requests.delegate_record; delegate messages use author_role 'membre' with the delegate as author_id. Client routing: no profile + active delegation → only /, /demandes, /demandes/nouvelle, /demandes/:id (isDelegatePathAllowed); no profile and no delegation → InactiveAccess. Direct request/referral inserts require public.is_member(); the profiles INSERT policy was dropped.
- Profile hardening (23 October): members may UPDATE only full_name, phone, language and notify_* on profiles (column grant); everything else is team-only through server functions. handle_new_member creates a profile only when raw_app_meta_data.account_kind is 'membre' or 'equipe' (set by createMember / inviteColleague with the service key): public sign-ups, referrals and delegates never get a profile. Referrals no longer create accounts: sendReferralInvite records a recommendation (member session, is_member RLS), the team contacts the person, creates the member, then converts the referral.
- Hardening (23 October, migration 0030): invoices are created only through public.create_invoice() (number and row in one transaction from public.invoice_counter, no gaps; next_invoice_number is retired); invoices.mollie_payment_id is unique. The Mollie webhook is idempotent (claim on profiles.mollie_subscription_id = 'en_cours:<payment>', subscription startDate one period after the first payment, stale/smaller payments ignored, paid invoices never downgraded, 500 on write failure so Mollie retries); rules in src/lib/billing-webhook-rules.ts (tested). The WhatsApp webhook secret and endpoint live only in Vault (notify_concierge_webhook_secret, notify_concierge_endpoint — set the production URL there on publication); the trigger sends only the request id and /api/public/notify-concierge re-reads the request; WhatsApp templates are used when WHATSAPP_TEMPLATE_REQUEST / WHATSAPP_TEMPLATE_MESSAGE are set. The team gate requires a signed-in team account, allows 5 failed attempts per 15 minutes (admin_gate_attempts) and binds the session to the user; admin RLS read/update policies were dropped (team reads go through server functions only). Links in e-mails and payment redirects use trustedOrigin() (src/lib/app-origin.ts). Dates use todayParis(). French typography (narrow no-break spaces) is applied by translate() for fr.
- Auth trigger note (migration 0031): GoTrue writes raw_app_meta_data in a separate UPDATE after inserting the user, so handle_new_member also runs AFTER UPDATE OF raw_app_meta_data (ON CONFLICT DO NOTHING). Never rely on app_metadata being present at INSERT time.
- Second review (23 October, migration 0032): status changes follow STATUS_TRANSITIONS (src/lib/team-request-rules.ts); a request with an invoice cannot be cancelled; invoices only for Confirmée/Terminée; proposals, proposal answers and series only on open requests. Deactivating a member cancels the Mollie subscription first; a plan change PATCHes it. Rejected subscription charges go to public.payment_failures (team dashboard, "Relancé"). Signature members require a concierge WhatsApp number; notifyConcierge tries the concierge then the common number (conciergeRecipients). Statements use the invoice amount when it exists, otherwise service + plan commission marked as an estimate. Referral and delegate invitations never reveal whether an address is already a client. Removing someone from the team disables their account.
- Voice (27 October, validated by Sasha): titles, labels and message signatures use « votre conciergerie » (as in the V4 mockup, e.g. « Votre conciergerie, à votre rythme. »); sentences where the house acts use « nous » (« Nous vous confirmerons… », « Nous vous proposons… »). Avoid « notre conciergerie ». Same rule in English (« your concierge » / « we »).
- Blocking fixes (29 October, migration 0033): a disabled account is cut off at once — RESTRICTIVE policy "Comptes désactivés exclus" (public.account_enabled(auth.uid())) on every member-readable table, sessions closed by public.revoke_user_sessions() (service role) on deactivation or team removal, payInvoice/activateAutoDebit refuse disabled accounts; disabled members land on InactiveAccess. New requests carry a client-generated id so a double send is a no-op (23505 treated as sent). WhatsApp alerts for new requests go through public.post_concierge_notification(), used by the member trigger and by generate_recurring_requests() (which also copies the series' last assigned concierge). Every alert that is not sent is stored in public.notification_failures (notifyConcierge) and shown to the whole team in « À surveiller » (resolveNotificationFailure, « Traité »). The concierge is named to a member only when one is assigned (name + WhatsApp on the profile), whatever the plan; otherwise « votre conciergerie ».
- Lots 1 and 2 (29 October, migration 0034): members have profiles.timezone (IANA, default Europe/Paris, editable by the member on /membership/langue and by the team on the member page via setMemberTimezone; list in src/lib/timezone.ts). Member-facing timestamps, greetings and "today" use getTimeZone()/todayIn()/dayOf(); the time of a booking (requests.scheduled_time) is the venue's local time and is never converted; the team UI stays on Paris time. Member-created requests are checked server-side by the check_member_request_values trigger (1–500 guests, date/time not past in the member's timezone; errors date_passee / heure_passee / couverts_invalides); delegate requests apply the same rules in createDelegateRequest. Request amounts lock once an invoice exists (lock_invoiced_amount) and an invoice is refused if the amount moved meanwhile (check_invoice_amount); invoicing requires a known plan. Mollie payments use Idempotency-Key headers; billingStatus/activateAutoDebit re-read the subscription and mandate at Mollie (interrupted debit can be reactivated). Statements are admin-only; removing a colleague releases their open requests to « À attribuer »; team lists are paged with fetchAll. .ics files include a VTIMEZONE block, parse free-text times and fold long lines.
- Team sign-in (29 October): the team signs in only with its Google Workspace account (@artdevie.co) through Lovable Cloud's managed Google OAuth (src/integrations/lovable, @lovable.dev/cloud-auth-js; Google must be enabled in More → Users → Settings → Google).
